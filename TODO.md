## x87 follow-ups

- [ ] **[P3] Extended-precision values silently change during display, comparison, and assignment.** With a live inferior, zxdb printed the finite value `0x1p2000L` as `inf`, printed the nonzero value `0x1p-2000L` as `0`, and reported that `1 + 2⁻⁶³` equaled `1.0`. The evaluator narrows both operands to binary64 before the operation. An assignment such as `x = x + 0` can therefore overwrite an exactly representable target value with a rounded one. Keep extended precision through formatting, arithmetic, comparisons, and integer conversions. LLVM’s `APFloat::x87DoubleExtended()` provides target-independent semantics. [Formatter](src/developer/debug/zxdb/expr/format.cc#L71) · [Binary operators](src/developer/debug/zxdb/expr/eval_operators.cc#L432) · [Integer conversion](src/developer/debug/zxdb/expr/cast.cc#L148)

- [ ] **[P3] The format check misidentifies IEEE binary128 on x86-64.** A single executable can contain both 16-byte `long double` and 16-byte `__float128`. I confirmed that zxdb printed a GCC `__float128` initialized to one as `0`. The new check interprets the low ten bytes as x87 based solely on size and architecture. Use the concrete target type and ABI to select the format, and identify ST register values from their register metadata. Preserve the raw display when the format is unknown. [Format detection](src/developer/debug/zxdb/expr/x87_float.cc#L25) · [Formatter](src/developer/debug/zxdb/expr/format.cc#L69)

- [ ] **[P3] Unary minus and logical negation still reject x87 values.** Both `print (-wide)` and `print !wide` returned “Unsupported size for unary operator” for a live `long double`. The unary float code handles only four- and eight-byte values. Implement negation by changing the x87 sign bit and logical negation by testing the extended value for zero. Cover both signed zeros and a nonzero value below the binary64 range. [Unary float operators](src/developer/debug/zxdb/expr/eval_operators.cc#L883)

- [ ] **[P3] Even an explicit cast to `double` can round incorrectly.** `X87ExtendedToDouble` first rounds the 64-bit significand to `double`, then scales it with `ldexp`. For `0x1.0000000000000002p-1075L`, the first rounding discards the bit that places the value just above halfway to the smallest positive binary64 subnormal. I compared the helper’s formula with a native cast under round-to-nearest. The formula returned zero and the cast returned `2⁻¹⁰⁷⁴`. Convert in a single rounding step and add this boundary case. [Conversion](src/developer/debug/zxdb/expr/x87_float.cc#L46)

- [ ] **[P3] The decoder treats unsupported x87 bit patterns as ordinary numbers.** For example, exponent `0x7fff` with a zero significand is an x87 pseudo-infinity. The decoder reports infinity because it discards the explicit integer bit when checking the fraction. A nonzero finite exponent with a clear integer bit can likewise appear as a regular number. These encodings can occur when inspecting raw ST/MMX state. Check the integer bit and report an unsupported encoding or NaN, consistent with LLVM’s x87 decoding. [Decoder](src/developer/debug/zxdb/expr/x87_float.cc#L39)
